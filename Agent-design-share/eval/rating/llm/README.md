# LLM 评分员代替人工完成的评分（2026-11-25）

**这不是人工评测。** proposal §4 要求由两名人类评分员或标注者完成这些评分。由于时间所限，改由两名 LLM 评分员完成，并列为与 proposal 的偏差。具体做法如下：

- 两名评分员都是 Claude Sonnet 5.5，各自独立评分（A 填 `_r1`，B 填 `_r2`）。
- 评分表与 `eval/rating/` 下给人工用的空白表完全相同，评分标准就是 `eval/README.md` 的「标注指南」。
- **盲评**：答案键（实验条件、模型分数、数据集标签）事先移出仓库。两名评分员各自在隔离的文件夹里工作，只能看到空白表、标注指南和已审核的参考库，看不到对方的结果。
- 要求逐行阅读后给分，不准用脚本或关键词规则打分。
- **评分员与被测模型不同源**：被评的反馈、提示、情境题等由 DeepSeek `deepseek-flash` 生成，评分员用的是 Claude，可以避免同一模型给自己打高分。
- **局限**：proposal 里「模型分与人工分的误差」在这里变成了「DeepSeek 与 Claude 之间的误差」，只能说明两个模型是否一致，不能代替真人的判断。建议组员抽查 20 行，看与 LLM 评分员是否一致。

## 怎么复现

```bash
python3 eval/rating/llm/merge.py /tmp/mianbi-rating/A /tmp/mianbi-rating/B   # 两名评分员的 *.ratings.jsonl → 本目录的表
cp <答案键目录>/*.key.jsonl eval/rating/llm/                                  # 答案键不在仓库里
.venv/bin/python eval/run.py stats eval/rating/llm/evaluator_rating.csv --metric correctness --a none --b weighted
```

## 结果

### 1. 评估器（proposal 的核心比较；40 例 × 有证据 / 无证据，36 个概念族配对 bootstrap）

| | 无证据 | 有证据 | 差（有 − 无），95% CI |
|---|---|---|---|
| 反馈正确性 | 4.05 | 4.29 | **+0.28 [+0.08, +0.51]** |
| 反馈有用性 | 3.74 | 3.73 | +0.01 [−0.09, +0.11] |
| 好回答的反馈正确性 ≤ 3（冤枉对的回答） | 10 / 20 | 6 / 20 | |
| 有缺陷回答的反馈正确性 ≤ 3 | 0 / 20 | 0 / 20 | |

- **模型分与评分员给的分**：平均绝对误差 0.44；模型分平均低 0.35，说明 DeepSeek 评估器比评分员更严。有证据时误差 0.42，无证据时 0.46。
- **两名评分员的一致性**：正确性 κ = 0.63，有用性 κ = 0.60，回答本身的分数 κ = 0.47（1–5 分的连续分值，原始一致率 0.53）。
- **结论**：与 DeepSeek 自动指标（迭代记录第 3 条）一致。证据的作用主要是让对的回答少挨冤枉，对抓出明显错误几乎没有影响。有用性没有差别。
- **引用支持度**：4.73 / 5（267 条）。两人原始一致率 0.82；κ = 0.39，偏低是因为几乎全是 5 分。

### 2. 资料相关性（448 对）

- 两名评分员之间 κ = 0.97，原始一致率 0.99。
- 两人与数据集标签的一致性都是 κ = 0.96，说明检索的 Recall@3、nDCG@3 用的标签可信。
- 组员的测试报告（`TEST_REPORT_2026-11-25.md`）发现：最初的 433 对只合并了 BM25、向量、混合 3 种检索，漏了 weighted。补上 weighted 前 3 名后多出 15 对，原有编号不变。两名评分员都把这 15 对判为不相关，与数据集标签一致。也就是说，加权挤进前 3 的资料确实都不相关，「公式 (1) 让检索变差」的结论不受影响。

### 3. 历史作答

| | 只看当前作答 | 看历史 |
|---|---|---|
| 修改建议是否针对历史问题（1–5） | 3.71 | **4.54** |
| 把已改正的问题说成仍然存在 | 1 / 12 | 0 / 12 |
| 点出反复出现的误解（评分员 B） | 0 / 8 | **8 / 8** |

- **变化标签**：两人 κ = 0.87。与数据集标签相比，A 是 κ = 1.00，B 是 κ = 0.87。
- **「点出反复出现的误解」两人分歧很大**：原始一致率 0.50，κ = 0。原因是理解不同：
  - A 的理解是「反馈有没有指出这个误解」，只看当前作答也能指出，所以两种条件都是 8 / 8。
  - B 的理解是「有没有指出这个误解是**反复出现的**」。
  - proposal 测的是 recurring-error detection，B 的理解是对的。标注指南已据此改清楚。这正是 proposal 要求「先报告裁决前的一致性」想发现的问题。

### 4. 个性化提示（12 组 × 通用 / 个性化）

| | 通用 | 个性化 |
|---|---|---|
| 是否符合偏好（1–5） | 2.94 | **4.75** |
| 有用程度（1–5） | 3.77 | 3.83 |
| 太直接，泄露了答案（两人都判） | 1 / 24 | **7 / 24** |
| 有事实错误 | 0 / 24 | 1 / 24（过山车：给出的物理原因有误） |

- 个性化确实更符合偏好，但**代价是更容易泄露答案**。泄露主要来自「希望点出关键词 / 关键术语」这一类偏好：模型把关键词点得太全，等于把答案说了出来。proposal 第 5 页把「提示泄露完整答案」列为风险，这里得到了证实（见迭代记录）。
- **两人一致性**：事实是否正确 κ = 1.00，是否太直接 κ = 0.65，是否符合偏好 κ = 0.63。

### 5. 情境题（37 道）

- 概念一致 4.47，能否作答 4.41，情境变化 3.82，难度 3.23（3 = 与原题相当），资料支持 4.32。
- **有问题的题**：5 / 37 道至少一项被两人都打到 ≤ 3 分，两人各自独立指出了相同的错误：
  - TIME_WAIT 题前提自相矛盾（由网关先关闭，却问另一端为什么有 TIME_WAIT）；
  - 共享单车博弈题的数字不一致；
  - 过山车 / 圆弧轨道题第二问算出来是 0 J；
  - WAL / sendfile 题在概念上硬凑；
  - 金刚石 / 石墨题偏离了原题概念。
- pH 题：「10 mL 稀释到 1000 mL」实际是 100 倍，答案却按 1000 倍算。两人的书面意见都提到了这一点，但只有 A 在「能否作答」上扣了分（A 给 2 分，B 给 5 分）。
- 生成的情境题目前没有自动核对答案（见迭代记录）。

### 6. 语音复盘总结（12 段）

- 忠实度 4.21 / 5。
- 5 / 12 段两人都发现了转写中没有依据的说法。典型问题：
  - 把转写错误（「布容」「B家属」）当成学习者的错误；
  - 把正确的定义说成错的；
  - 编造了一个「10%」的例子。
- 漏掉的要点平均 0.08 条。

### 7. 闪卡（20 张）

- 资料支持 5.00，事实正确 20 / 20，覆盖核心概念 4.47。
- 两人一致性：资料支持、事实正确都是 κ = 1.00；覆盖核心概念 κ = 0.64。
